# Review context before execution

**What does this agent know? / Cosa sa questo agente?** opens before a chat message, a task start or resume, a repository start, or an AI-drafted dependency plan. It shows the prepared context for each participating role, its configured provider and execution destination, and the applicable call allowances. Preparing or refreshing this preview makes no AI call and reserves no call budget.

Read the selected memories and document passages, adjust the controls if needed, then choose **Refresh preview**. **Confirm and start** becomes available only after the current choices have been prepared and the budget preflight allows them. Cancelling closes the preview without starting the work. Ordinary access, scope, provider, and runtime checks still apply when execution starts.

## What the controls mean

A selected memory shows its title, owning scope, version, bounded content and recorded source. Document entries show the selected passages, page or line references, and an HTTP(S) origin link when available. Provenance records where context came from; it does not establish that the content is independently verified. Excerpts can be partial, and the inventory is not a byte-for-byte display of the complete system prompt.

Unchecking a memory or source excludes that record from this work's additional context for every participating agent. It does not delete, edit, unshare, or unconfirm the original. Exclusions narrow what the agent already has permission to read; they cannot grant access to another scope, agent-restricted memory, stale source, or disallowed provider. An included workflow remains a selected procedure; its instructions are not independently removable with a memory checkbox.

For chat, the coordinator is always included. Additional specialists are opt-in, and the coordinator can request contributions from up to three of the selected specialists. Selecting a specialist authorizes a possible contribution; it does not guarantee that a call will be made. Each selected role is prepared and checked separately. The displayed maximum is one coordinator call plus at most three specialist calls.

Chat also offers **Include the authorized conversation history**. Turning it off removes earlier messages from this turn's context, while the new message is still sent. With history enabled, the preview contains up to the latest 24 eligible messages per role, capped at 9,000 characters per message. Messages derived from an excluded memory/source are removed, as are messages whose recorded evidence is now unavailable, stale, revised, unshared, or unauthorized for that role. The conversation itself remains saved. These checks use recorded evidence; they cannot detect every independently typed or copied occurrence of the same information in a brief or message.

When the active scope has projects, chat can attribute its calls to a selected project. The project must belong to that scope. Without a project, chat uses the installation's daily allowance. Provider and local/paired-computer destinations come from configuration and are shown for review; the preview does not silently choose an alternative service.

## Context by kind of work

| Work | Prepared context and execution boundary |
| --- | --- |
| Chat | The new message, selected ready workflow and per-use fields, authorized history, and selected memories/document passages for each allowed role. Specialist instructions are generated by the coordinator after execution begins. |
| Text task | Every unfinished step's agent and provider, selected memories/documents, the saved workflow and values, project data, task brief, requested revision feedback, completed steps, and approved predecessor deliveries where required. The preview shows available references and predecessor deliveries; it cannot show future step outputs. |
| Repository | Editor and, when available, independent reviewer context, configured destinations, the stored base commit and check configuration. The editor will also read the isolated repository files and run the separately approved checks. Memory/document checkboxes do not filter repository files. The reviewer receives the generated patch and its evidence after editing. |
| Dependency plan | The coordinator's selected project context and one planned call to draft the proposal. Committing the resulting proposal creates queued tasks without another AI call. Each task later needs its own start preview. |

A repository preview may report that independent review is unavailable. That condition is visible before start; it is not replaced silently with a different reviewer. Editing, checks, and later human patch review retain the normal repository lifecycle. Previewing does not run Git checks, prepare a checkout, test provider credentials, or establish that the execution computer will remain available.

## Inherited evidence and reruns

A later step can receive text generated by earlier steps. A dependent task receives approved predecessor deliveries, and a task drafted through a plan retains the proposal's source evidence. Those results may already incorporate a memory or document even when fresh retrieval would not select it again.

Existing required evidence is therefore retained and revalidated. References already used by a necessary completed or inherited result are locked where they appear among the preview's entries. An attempt to exclude such evidence is rejected rather than pretending that removing the fresh passage removes it from the existing output. Some inherited references may only be represented in the dependency/evidence warning rather than a new passage card. To stop depending on those results, prepare an independent assignment with an appropriate brief and no inherited dependency.

Task exclusions are saved with the task and retained through pause, restart and requested revisions. A new preview can change eligible choices; a restart alone does not clear exclusions or remove inherited plan/dependency evidence. Resume keeps completed steps, while restart clears step outputs and retains earlier deliverable/review history. Changed source versions or revoked permissions can block resumption. A changed workflow requires a new task prepared from its current version and fields.

Repository revisions retain the previous selection and the assignment's budget ancestry. Every explicit start still requires a fresh preview. Starting work never resets its lifetime call usage, and a failed or cancelled attempt does not restore consumed allowance. See [AI call budgets](BUDGETS.md) and [workflow fields](WORKFLOW_FIELDS.md).

## Receipt expiry and revalidation

The server stores the prepared input and a digest of the complete prepared plan and budget snapshot. It returns an opaque `previewId` and an `expiresAt` timestamp. A receipt:

- expires after **10 minutes**;
- authorizes one matching start and is consumed on successful preflight;
- exists only in server memory, so a server restart removes it;
- can be evicted when more than 100 previews are prepared.

At start, the server rebuilds the plan from its own stored receipt input and compares it with the previewed plan. Changes to the work, context or history, permissions, source/workflow versions, service assignment, destination, or budget snapshot can require a refreshed preview. A receipt for a different kind, task, message or project is rejected. Clients cannot supply an authoritative prepared context through the execution endpoint.

The allowance check is advisory. It makes no reservation. Every actual provider dispatch performs the durable atomic budget check again; another call or setting change can exhaust capacity after preview. The displayed counts constrain studio dispatches, not a monetary invoice or every internal Codex model/tool operation. Missing token reports remain unknown. See [budget enforcement](BUDGETS.md).

## API flow

`POST /api/execution/preview` is an owner-authorized, CSRF-protected JSON request and requires an idle studio. It accepts one of these targets, optionally with `selection`:

```text
chat       { kind:"chat", message, scopeId, workflowId?:null|id,
             agentIds?:["nova",...], projectId?:id|null,
             inputValues?, expectedWorkflowVersion? }
task       { kind:"task", id, expectedVersion? }
repository { kind:"repository", id, expectedVersion }
plan       { kind:"plan", projectId, brief }
```

The selection object accepts only `excludeMemoryIds`, `excludeSourceIds`, and `includeHistory`. Exclusion lists contain at most 200 unique record IDs each. `includeHistory` is a chat control. Per-use workflow fields are supplied during chat preview or when creating the task/routine; they are validated against the authorized workflow version.

The response includes `previewId`, `expiresAt`, work identity, `selection`, participating `agentIds`, `requiredCalls`, `budget`, and per-step context/provenance/provider/destination details. Repository responses can include `reviewUnavailable`.

Pass the receipt to the matching execution route:

```text
POST /api/chat
  { message, scopeId, workflowId:null|id, previewId }

POST /api/tasks/run
  { id, expectedVersion?, previewId }

POST /api/repositories
  { action:"start", payload:{ id, expectedVersion, previewId } }

POST /api/plans
  { action:"draft", payload:{ projectId, brief, previewId } }
```

A missing, expired, mismatched, or stale receipt returns HTTP `409` before dispatch. Refresh and review the preview; do not automatically repeat a paid start. Runtime/provider failures can still occur after a valid start. Explicitly enabled autonomous routines use the existing scheduling authorization and execution checks rather than an interactive dialog for each occurrence; the preview requirement above applies to owner-initiated HTTP starts.

For the surrounding endpoints, see the [HTTP API](API.md). Use [local search](SEARCH.md) to inspect saved originals without preparing or starting any execution.
